## G-1 语义层知识不可达窗口（四路全 miss 且文档无对应文本）

- **来源**：设计讨论（2026-10-19，语义检索分层问答）。
- **问题**：语义语料不进文档知识库（D23 分层：源端事实在 `sem_*` 表、人工内容在 `curated_json` / 别名、表列详情不落库），**docs RAG 对语义知识零兜底**；语义层 recall 的全部上限 = 自身检索面：L0（1500 token 预算）→ L1 `annotate`（AC 自动机，确定性）→ L2 `search_entities`（别名精确 > 前缀 > 拼音 > 向量）→ L3 模糊兜底。**四条路全 miss 时，该知识本轮不可达**，不存在其他通道。
- **触发场景**：实体的名称 / 别名未配置、用户用词完全对不上（M2-S3 前 `search_entities` 只有别名精确与前缀——拼音与向量排序排在 M2-S3，design §8），**且该知识只存在于源系统配置、任何上传文档都没写过**。典型：「模板 X 落在哪张表、哪个字段」——`backed_by` / `maps_to` 关系只活在模板中心，文档从未叙述。反之，若语义 miss 但文档里有文字（制度、口径类），docs RAG 仍能兜住文字证据，丢的只是结构化上下文（规范名、定义、关系图），不是全部信息。
- **设计现状与对冲**：三层渐进披露本身就是主要对冲——L1 miss 后 L2 是 agent 主动检索路且检索面更宽（design §5.9 第 2 层明确为「第 1 层未命中」准备）；识别评测集门槛 AC+模糊 recall@3 ≥ 0.92（**即明示接受 ~8% miss**——设计将缺口定性为词典治理问题而非检索架构问题）；构建报告列孤立节点 / 歧义别名；agent 日志高频未识别词回流成待补别名（design §10「人工内容无人维护」行，**季度运营回顾节奏**）。
- **残留缺口**（接受的）：单轮内四路全 miss 即答不出；回流周期季度级，新缺口最长暴露一个季度；识别评测集以 span 标注为主，测不出「答案只在语义层、文档无对应」样本的**端到端可达性**。
- **收窄动作**（未排期，不构成决策变更）：
  1. `search_entities` 的拼音 / 向量排序从 M2-S3 前移到 M2-S1/S2（模糊索引构建本就挂 S2；L1 miss 后它是唯一加宽的检索面）；
  2. 回流口径从「annotate 未识别词」扩展到「`search_entities` 空结果的查询词」——agent 主动来搜还没搜到，是更明确的缺口信号；
  3. 识别评测集（150~200 条）增加一类「答案只在语义层、文档无对应」的端到端样本，直接度量本缺口。
- **重开条件**：回流日志中同类查询持续高频出现；或 M2-S3 评测 recall@3 不达标且主因是别名覆盖（词典治理失灵的信号）。

## G-2 模糊兜底层的触发者与消费者未闭环

- **来源**：设计讨论（2026-10-19，G-1 分析中发现的规格缺口）。
- **问题**：第 3 层模糊兜底 `fuzzy=true` 才跑（FR-S3），结果 `via='fuzzy'`、置信度低于第 1 层，**中间件不自动注入，「只作候选提示」**（design §5.9）。但未写明闭环的两端：**谁传 `fuzzy=true`**（中间件每轮都传？还是不传？），以及** candidates 谁消费**——中间件注入规则只覆盖两类：confidence=1.0 非歧义命中（②）与歧义命中注入候选列表（③），`via='fuzzy'` 的候选不在其中。若中间件调了 fuzzy 但结果丢弃、且没人引导 agent 自己调 `annotate(fuzzy=true)`，第 3 层形同虚设。
- **影响**：实现期随手处理的失败模式是「谁都不传 fuzzy / 传了结果被丢」，实际 miss 窗口宽于评测口径——**G-1 的 recall@3 ≥ 0.92 假设第 3 层在工作**，它空转则该门槛名不副实。
- **收窄动作**：M2-S3 实现前二选一澄清，并补进 design §6.3 中间件规则：①中间件注入 candidates 一行提示（低信任措辞，计入本轮 600 token 预算）；②`annotate` 工具描述明确引导 agent「L1 无命中且判断有业务对象时自行调 `annotate(fuzzy=true)`」。二者可并存。
- **重开条件**：无——属实现前必须澄清的规格补写（预计不构成决策变更，随 M2-S3 排期）。

## G-3 restricted 实体静默缺失：agent 不知道自己缺信息

- **来源**：设计讨论（2026-10-19，G-1 讨论衍生；设计文档未展开此层）。
- **问题**：restricted 实体对无权调用方「表现为不存在」——annotate 不返回 span、`search_entities` 别名命中不可见、`get_entity` 404、关系展开不出现（T-S9，design §6.3 权限口径③）。这是防存在性泄露的正确选择，但次生效应是**全程无信号**：用户问题核心恰是 restricted 实体时，agent 得到的不是「无权限」而是「不存在」，可能给出**看似完整、实则缺关键对象**的回答——比显式拒绝更隐蔽，且与 G-1（知识真缺失）在 agent 侧不可区分。
- **设计现状与对冲**：restricted 定位「极少数」敏感对象（design §6.3），暴露面小；其访问进权限审计（outbox）——数据基础已在。
- **残留缺口**（接受的）：无权用户得到的缺料回答无法在交互层识别，只能事后从审计与用户负反馈回溯。
- **条件性扩大（2026-10-20 预登记，#37 实体维度 ACL 演进缝，未触发）**：#37 将实体维度 ACL 延后为演进缝；一旦触发启用，本条机制按其 T-S9 泛化规格原样作用于**维度不可见实体**——不可见集合从「极少数 restricted」扩大为**区域级实体集合**（调用方无授权维度的整批业务对象，如全部海外模板）。届时：①本条「暴露面小」的接受依据不再成立，须重估；②无技术对冲的结论不变——存在性 / 计数提示即泄露（T-S9 / docs 侧 P1-8 口径），#37 评论已据此写死「表现为不存在 + 统计按可见子图 + 维度过滤不走 outbox」；③典型症状是漏授权 / 未授权用户的核心业务问题常态化「查无此物」且与 G-1（知识真缺失）更不可区分，对冲仍只有审计回放与用户负反馈。
- **收窄动作**（运营口径，非代码）：审计侧关联「无权 restricted 访问 + 同会话后续追问 / 负反馈」模式，命中即人工介入。**工具描述层不提示**——提示即泄露存在性，与 T-S9 设计冲突，明确不做。
- **重开条件**：restricted 实体数量显著增长；或出现因静默缺失导致的实际误导案例（此时需评估回答层显式化方案，属决策变更）；或 #37 实体维度 ACL 演进缝触发实施（不可见集合扩大为区域级，须重估本条接受依据）。

## G-4 L0 注入陈旧性：dict_rev 记录了但没闭环

- **来源**：设计讨论（2026-10-19，通读 §6.3 时发现）。
- **问题**：agent 构建期调 `GET /semantic/l0` 把核心术语写进 system prompt 并**记录 `dict_rev`**，端点也返回 `dict_rev`（design §6.3 步骤 1 / §6.2）——记录的意图显然是比对失效，但**刷新机制未指定**：谁轮询、多久一次、还是构建钩子触发。L0 内容（核心术语定义）变更后，存量 agent 会话的 system prompt 保持旧版，最长滞后 = agent 服务重建周期。
- **影响**：L0 变更频率低（YAML PR 评审节奏），故严重度低；但若实现时忘记闭环，术语修订会长期滞留在 agent 常驻上下文里，与「构建报告 / 评测回归」的治理口径脱节。
- **收窄动作**：M2-S3（agent 中间件从本地 AC 切到服务端 annotate）实现时一并定：低频轮询比对 `dict_rev`（如小时级）即可，无需推送。
- **重开条件**：无——属实现细节补写，随 M2-S3 排期。

## G-5 容器化重部署数据易失：裸机形态假设与快照恢复引导缺口

- **来源**：设计讨论（2026-10-19，部署持久性问答：SQLite 数据在重启 / 重部署后是否保留；用户判断部署平台「重新部署可能会重新分配一个容器」）。
- **问题**：NFR-1 部署形态假设裸机 Linux——1 个 FastAPI 进程 + 1 个 worker 子进程 + 1 个 SQLite 文件，容器只是 MinerU 的升级路径而非依赖（**v0.7 后外部依赖为模型 API 网关——嵌入/重排不再有 TEI 容器升级路径，D12 修订**）。若实际平台为**易失容器**（每次重新部署分配新容器、未配持久卷），则全部持久化状态——`data/lattice.db`（含 `-wal` / `-shm` 边车）、`data/objects/` 原始文件、按月审计分库——都落在容器可写层，**容器销毁即整体丢失**。重启进程 / 重启机器本身安全（SQLite 是文件库，WAL 模式重开自动回放边车）；`synchronous = NORMAL` 下进程崩溃安全，但断电 / 内核崩溃可能丢 WAL 中最近未 checkpoint 的提交（秒级，只丢不坏）。
- **设计现状与对冲**：NFR-10 已定 `VACUUM INTO` / online backup 定时快照 + `data/objects/` 一并备份（RPO ≤ 24h / RTO ≤ 4h，恢复演练进 runbook）——**快照机制已在，本缺口不是「没有备份」**。另：语义层源端事实可从源系统重同步、YAML 覆盖层真相在 Git（可再生）；不可再生面收敛为上传原始文档、解析产物与嵌入向量（CPU 重新摄取贵）、任务状态、审计库。
- **残留缺口**：NFR-10 未指定**快照存放地**（须在容器生命周期之外，与容器同亡等于没备份）与**恢复引导**（「导入」步骤）；无关停前最终快照钩子；且 NFR-1 的裸机假设与实际平台形态不一致——修正 NFR-1 / NFR-10 / D2 属决策变更，需走 issue 流程（本条先立项登记）。
- **收窄动作**（未排期，按序）：
  1. 先确认平台是否真无法挂卷——named volume / bind mount / PVC 在容器重建后存活，是首选正解；同时明确**排除 NFS / SMB 直接放 `lattice.db`**（SQLite 锁机制在网络文件系统上不可靠，比没卷更危险）；
  2. 确无卷则补三件：快照目的地定容器外存储（NAS / MinIO 等 S3 兼容端点 / sftp 固定主机）；启动自恢复（`data/` 为空且配置了快照地址 → 拉取解包 → 照常跑 `user_version` 迁移，旧快照配新版本自动补齐）；SIGTERM 钩子关停前最终快照（计划内重部署丢失窗口≈0，平台强杀退化为上次定时快照）；
  3. 或直接引入 Litestream（单二进制伴随进程：WAL 持续流式推 S3 兼容 / sftp、启动自动 restore、RPO 秒级）——非常驻外部服务，不破坏零中间件纪律；
  4. runbook 补两坑：运行中手工备份必须走 backup API / `VACUUM INTO`（只 `cp` 主库不拷 `-wal` 会丢最近事务）；回滚部署时快照 schema 可能比二进制新（迁移只前进会卡住）。
- **重开条件**：部署平台确认可挂卷（本条直接闭环）；或发生一次重部署数据丢失事故；或库规模增长使小时级快照不再可行（需转 Litestream 类持续流式方案）。

## G-6 PG 后端已知差异：FTS 评分函数与向量索引维度上限（D24）

- **来源**：[issue #41](https://github.com/yq3/lab/issues/41) 决策 2（2026-10-21，存储后端双实现）。
- **问题**：D24 把 PostgreSQL+pgvector 升格为正式后端后，两处与 SQLite 后端不等价：①**FTS 评分函数不同**——SQLite FTS5 是 `bm25()`，PG 原生只有 `ts_rank`/`ts_rank_cd`（真 BM25 要 ParadeDB `pg_search`，公司托管 PG 大概率不让装扩展），两后端 BM25 路排序**不逐字一致**；②**pgvector 索引维度上限 2000**——现网 `qwen3-embedding-4b` 为 2560 维，`vector(2560)` 建不了 HNSW/IVFFlat；③HNSW 带 ACL 过滤有欠召回风险（授权窄的用户可能拿不满 top-k）。
- **触发场景**：①M1 PG 后端追平全矩阵时，同一黄金集在两后端 recall@k/MRR 有系统性偏差；②M0b PG spike 建索引时直接报错；③规模增长后 PG 侧启用 HNSW。
- **设计现状与对冲**：①RRF 只看名次、融合后 top-k 集合差异被大幅抹平，TEST-CASES 排序类断言按「名次集等价」执行（A-17）；PG 侧用应用层 jieba 预分词 + `to_tsvector('simple', …)` 五列 GENERATED + 加权 `ts_rank` 求和（不依赖 zhparser/ParadeDB）；②`halfvec(2560)`（fp16，索引上限 4000、存储减半）/ MRL 截断 ≤2000 / 不建索引走精确扫描——三条出路见本条与 design §10「PG 后端差异」行（design §4 注仅指向本条）；③**精确扫描起步**（与 SQLite 暴力扫语义完全一致），HNSW 启用需 pgvector ≥0.8 `hnsw.iterative_scan=strict_order` 并重跑越权矩阵；**越权安全不受①②③影响**（WHERE 仍生效 + 返回前二次断言），受影响的只是召回完整度与排序一致性。
- **残留缺口**（接受的）：两后端检索质量不承诺逐分一致，黄金集须分后端校准（M1 小型集 / M3 完整集各一份基线）；PG 索引化时机与 halfvec 质量损失未标定。
- **收窄动作**（未排期）：①M0b PG spike 先确认公司 PG 扩展白名单与版本（需求待决-6）；②M1 PG 全矩阵时记录两后端 recall@10/MRR 偏差，>2pp 则评估 `ts_rank_cd` 加权重调或 pg_search 可行性；③halfvec vs 精确扫描在 10 万块 P95 对比进 TC-PERF。
- **重开条件**：两后端黄金集偏差持续 >2pp 且 RRF 抹不平；或公司 PG 明确允许 ParadeDB（届时改为真 BM25 可消除①）；或 PG 侧 10 万块精确扫描 P95 超标必须索引化。

## G-7 网关 rerank 端点形态未确认：OpenAI 无 rerank 标准

- **来源**：[issue #41](https://github.com/yq3/lab/issues/41) 决策 1 / 待确认-1（2026-10-21）。
- **问题**：D12 修订把重排也外置为 API，但 OpenAI API **没有 rerank 端点**——各家是 Cohere 风格 `/rerank`、TEI `/rerank`、vLLM `/score`，Qwen3-Reranker 系还是生成式打分（部署形态与嵌入不同）；公司网关是否提供、提供哪种**未确认**（需求待决-5）。
- **影响**：FR-2 的 rerank 阶段无实现落点时 M1 管线无法闭环；若硬做 pointwise 走 chat 模型打分，延迟远超 NFR-8 的 1000ms 预算。
- **设计现状与对冲**：Reranker provider 接口**必带 `none` 实现**（跳过重排用 RRF 序，TC-EMB-05）——M1 可在无 rerank 下先闭环；rerank 不可达同样降级（TC-EMB-04）；研究基线（Azure BEIR：混合 48.4 → +semantic ranker 50.0）说明 rerank 是增益项而非可用性前提。
- **残留缺口**：无 rerank 时检索质量基线偏低（约 1.6 NDCG 点量级），黄金集口径须标注「含/不含 rerank」两档。
- **收窄动作**：M1 前向网关团队确认端点与模型；确认后按形态实现对应 provider（接口不变）；无则 M1 验收以 none 档为准、rerank 列为 M2 增益项。
- **重开条件**：网关提供 rerank（本条闭环为 provider 实现任务）；或评测显示无 rerank 时召回质量不达 M1 门槛（届时评估自部署 TEI reranker——违背 D12「模型不在本机」须走决策变更）。

## G-8 嵌入模型治理三件开放点：MRL 截断、指纹阈值、迁移方案

- **来源**：[issue #41](https://github.com/yq3/lab/issues/41) 决策 1.2~1.4（2026-10-21）。
- **问题**：D12 修订引入三项机制，参数/选择均未标定：①**MRL 前缀截断**——Qwen3-Embedding 模型卡支持 32~2560 可变维度，客户端取前 k 维 + 重归一化可把存储/扫描压回 1024 量级，但质量损失未用本项目语料验证（且只解决成本、不解决跨模型兼容）；②**指纹探针阈值**——哨兵文本余弦偏差「超阈值」的阈值数值未定（太松漏报换底模、太紧误报网关正常版本微调）；③**重嵌入迁移方案**——方案一（置空重建、迁移期向量路降级）与方案二（`chunk_vectors` 分表蓝绿、零降级）二选一挂在 M0b 分表实验。
- **触发场景**：①10 万块 2560 维 P95 超标或存储压力；②网关升级底模或正常微调版本；③首次换模型。
- **设计现状与对冲**：①design §5.3 标签带 `:trunc` 后缀区分截断向量，与不截断向量不混算；②探针拒绝写入 + 告警是保守方向（误报代价 = 人工确认后换标签重嵌，不丢数据）；③两方案都保证 BM25 全程可用（useful-early），差别只在向量路降级窗口；TC-EMB-06 按方案一断言（M2），方案二选中则回写用例。
- **残留缺口**：三项数值/选择在真实语料（待决-1）与 M0b 实验前无法定；指纹阈值在模型侧无文档可依，只能经验标定。
- **收窄动作**：①M1 小型黄金集到位后跑 2560 vs 1024 截断 recall@10/MRR 对比，损失 ≤1pp 则允许截断为可选配置；②指纹阈值先取保守值（如余弦 < 0.99 告警、< 0.95 拒绝）并在 M1 用网关正常版本抖动数据校准；③M0b 分表实验把「模型迁移蓝绿」列为判据之一（design §8 M0b-2）。
- **重开条件**：真实语料到位（待决-1）；或发生一次网关换底模事件（用真实偏差校准阈值）；或首次换模型需求出现（届时方案选择必须定）。

## G-9 间接 prompt injection：输入侧防护 MVP 不实现，出站外传与 agent 上传传播向量无对冲

- **来源**：设计讨论（2026-10-21，权限设计评估（FR-4 / design §6.3 ACL 收益辨析）衍生）。
- **问题**：NFR-6 明示 prompt injection 为已知缺口、MVP 不做输入侧防护（仅「agent 来源标注先行」一句原则）。检索内容进入 LLM 上下文后无「数据 / 指令」分离：语料中被蓄意植入的指令可被消费端 agent 执行——被注入的 agent 持**合法委托 token**（D18）外传当前用户可见内容（confused deputy：身份、token、权限全程真实，被污染的只是读到的指令，维度 ACL 判定全程「正确」——路径持证走正门，不经过任何越权）；且消费端 agent 并非纯只读——经上传凭证（design §6.3 agent 侧时序，#33 P1-3）具备写路径，被注入 agent 可将含注入的文档植入组织可见语料，等其他用户的 agent 检索命中，形成**语料内传播向量**（凭证绑定 sub+org+服务身份解决追责，不阻止上传本身）。
- **触发场景**：①低权成员上传含注入的文档（上传本身合规——文档在其授权维度内），高权用户的 agent 检索命中后按植入指令汇总 / 外传该用户可见内容；②被注入 agent 经上传凭证把注入文档写回语料，扩散到更多用户的检索面；③上传者诚实但内容由外部撰写（邮件、供应商合同、网页剪藏）——上传纪律与维度 ACL 对这类来源均不设防。
- **设计现状与对冲**：架构级防御已在，且属行业共识中唯一有效的一类（「假设模型会被操纵，让操纵不产生后果」）——**维度 ACL 把被劫持 agent 的外传上限框在受害者可见集合**（爆炸半径 = 权限面，而非全组织语料）；上传凭证制绑定 sub+org+服务身份 + owner 可追溯 + 查询级审计 / 权限事件 outbox（事后取证与追责）；agent 其余工具面只读（search / fetch / annotate 等）。**行业现状**（2026-10 核对）：注入无「不损失可用性且有完整安全保证」的单一解——大厂 2025 年公开承认、OWASP LLM Top 1；检测类防御（扫描 / 守卫模型）处军备竞赛（改写、跨块拆分、编码绕过是常态，守卫模型自身可被注入），CaMeL 类架构级方案（DeepMind 2025，能力模型 + 控制流 / 数据流分离）有约 7pp 任务完成率代价且要求重构应用形态。
- **残留缺口**（接受的）：①**出站通道零覆盖**——agent 输出外发前无 DLP / 内容审查（CaMeL 亦未完全解决的机密性通道），ACL 只限流、不堵漏；②**上传内容无隐藏文本检测**——「人看到的 ≠ 模型读到的」这一蓄意注入最强签名（白字 / 零宽字符 / 隐藏图层 / 批注 / 图片内文字）无任何检测；③来源标注无落地形态；④agent 上传路径的传播向量无对冲。
- **收窄动作**（未排期，不构成决策变更）：
  1. parse 阶段（design §5.3）加**确定性隐藏内容检测**：渲染可见文本 vs 抽取文本差集（白字 / 极小字号 / 页外文本 / PDF 隐藏图层 / docx 隐藏属性与批注 / 零宽与同形字符 / OCR 图片文字）——合法文档无理由包含不可见文本，误报极低，高置信内容直接剥离或拒收并提示上传者；
  2. quality 阶段（design §5.4）并列**注入风险信号**：不阻断（本语料为制度 / 操作指南，祈使句密度天然高，阻断式误报不可承受），落 chunk / 文档元数据，检索返回时随来源标注带给消费端 agent——NFR-6「来源标注先行」的具体化；
  3. 出站侧 DLP：agent 输出外发前内容审查（堵残留缺口①）；
  4. agent 经凭证上传的文档默认打**低可信来源标记**（消费端 agent 据此降低信任），抑制传播向量。
- **重开条件**：agent 获得上传外的行动工具（邮件 / 工单 / 写回业务系统）——风险从「外传可见内容」升级为「代用户行动」，届时须升格为决策变更立项；语料中外源内容（邮件 / 合同 / 网页剪藏）占比显著上升；审计回放发现实际注入事件；或发生一次因注入导致的信息泄露事故。
