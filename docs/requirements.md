## 1. 项目定位

**一句话**：私有化部署的企业内部知识库系统（本体）+ RAG 检索能力（能力面），**消费者以 Agent（deepagents）为主、人工检索测试为辅**。

四个定位要点：

1. **本质是知识库，不是 RAG 引擎**。核心资产是文档、权限、维度元数据与摄取管线（canonical 真相）；向量索引只是可重建的投影，检索配方是可替换的能力层。这决定了存储与治理优先于检索花活。
2. **agent 住客户端，知识库做工具服务器**（quivr V2 的反转姿态）：不在本系统内做 agent 循环、聊天界面、workflow 编排；把检索、溯源、鉴权做成值得 agent 信赖的 MCP 工具面。
3. **轻量自建，不做平台**。调研结论：开源五平台（ragflow/dify/anything-llm/quivr/kotaemon）的文档级权限全部缺位、面向人的产品面本需求用不上；自建薄服务可全部覆盖「检索质量 + 治理 + 工具面」三件事。
4. **双层知识供给中的文档知识层（2026-10-16 重定位）**。企业 agent 需要两类知识：**术语理解**（黑话/名词概念/模板名/报表项/表字段映射——结构化条目，精确匹配为主）由姊妹项目 [glossary-agent](../../glossary-agent/) 承担（AC 自动机词典 + 三层渐进披露 + Git YAML/PR 治理）；**文档知识**（政策/操作指南等非结构化内容的语义检索）由本系统承载。两层并行建设、MCP 并挂集成，分工与集成决策见 D17。

性质与投入：lab 仓库 POC 先行，验证后拆仓演进；**全职投入**，MVP 预估 7~8 周（§8）。

## 2. 背景与调研基础

选型判断全部锚定 `research/enterprise-rag/` 调研基线（2026-10 冻结），对本项目影响最大的结论：

| 调研结论 | 对本项目的塑形 |
|---|---|

| 检索配方已收敛：双路召回 → RRF(k=60) → cross-encoder 重排（喂原文、分数归一）→ 引用溯源（dim04 + Azure/Anthropic 量化背书） | 检索层不发明轮子，标准配方落地 |
| 解析双服务拓扑：MinerU 管扫描件、docling 管原生文档（dim02） | 本项目扫描件少、Office/TXT 为主 → 简化为 docling 为主、MinerU 懒加载 |
| 中文 BM25 引擎分野 + FTS5 无内置中文分词（dim03） | SQLite FTS5 + jieba 预分词方案，M1 用真实 query 验证中英混排效果 |
| 控制面/数据面分离、摄取任务化、索引可重建是五平台共识（dim01） | 单进程 + worker 子进程 + 任务表的最小实现 |
| OneRAG（126⭐，MIT）评估：形似神不似 | 不采用；借鉴两处——MCP server 模块结构、PDF 解析质量门（mojibake 检测三档处置） |
| **glossary-agent 设计**（lab 仓库，2026-09：Anthropic 16 篇深读 + ChatBI 语义层模式）：术语层方案已完成、POC 未启动；Anthropic Contextual Retrieval 双侧互证（BM25 利短术语 / hybrid+rerank 利文档） | 本系统定位为双层知识供给的**文档层**，与术语层（glossary-agent）并行建设、deepagents 双 MCP 并挂集成（D17）；表名字段名类走术语侧活查询，不进本系统 |

## 3. 用户与场景

| 角色 | 说明 |
|---|---|
| 上传者 | 企业员工，经上传页面（或 agent 代传）投喂文档：先选知识库，再选数据维度，查看处理状态与质量报告 |
| 检索用户（人） | 经检索测试页做简单检索验证（上传后自查），可按知识库过滤；不是聊天问答界面。**同一用户可属多个组织**，在界面上切换组织（左上角），角色与维度授权随组织切换 |
| **Agent（deepagents）** | 企业内部独立部署的 agent 服务（LangChain 系），LLM 走企业内部网关；经 MCP 调用本系统，**代人检索**——请求携带所代表用户的身份 |
| 组织管理员 | 组织内管理知识库、维度定义、用户与维度授权 |
| 系统管理员 | 跨组织：创建组织、指定组织管理员 |

量级：数百用户；语料百万 chunk 以下（超出则走存储升级缝，见 NFR-5）。

核心场景流：

```
人工上传（选知识库 + 选维度）─┐
                    ├─→ 摄取任务队列 → worker：解析→切分→嵌入→入库
agent 经 MCP 上传 ──┘         │（过程中：区分度检测 → LLM 补关键词 → 质量报告提示人工）
                              ▼
人（检索测试页，可按库过滤）─┐   SQLite：元数据 + FTS5 + 向量 + 维度/权限字段
                 ├─→ 检索管线：双路召回 → RRF → rerank → 维度 ACL 过滤（引擎内下推）
agent（MCP，带    │         → 返回带 chunk_id 溯源的结果 + 审计落库
用户 token）─────┘
```

**层级模型（自上而下）**：组织（业务单元，各自一套维度定义与知识库）→ 知识库（业务分组与管理单元，**不承担权限**）→ 文档（权限挂点：维度标签 + owner）→ chunk。

## 4. 语料画像

- **语言三态并存**：纯中文、纯英文、中英混排的文档都有；用户 query 同样三态（含「中文问题带英文术语」的常见形态）。嵌入选型、分词、评测 judge 均按双语设计。
- **格式分布**（按占比从高到低）：纯文本/TXT、Excel、Word、PPT；PDF 少量（原生为主，**扫描件不多**）。
- **来源**：人工上传 + agent 上传；后续可能对接企业系统自动增量同步（演进项，初版不做）。
- **生命周期**：文档会更新——初版只支持人工重新上传覆盖（内容哈希去重、按文档重索引）；删除同理。
- **上传纪律**：一份文件内的数据若分属不同数据维度，**拆成多个文档分别上传**（上传时各自选维度）。不做行级/块级权限（§7 决策 D4）。

## 5. 功能需求

优先级标注：〔M0〕骨架周 /〔M1〕核心能力 /〔M2〕生产化 /〔M3〕质量防线（对应 §8 里程碑）。

### FR-1 文档摄取〔M0 骨架，M2 生产化〕

- 上传接口：REST（人，multipart）+ MCP `upload` 工具（agent，**传文件引用或预签名 URL**，不经 base64——issue #31 P1-8）；上传时必选**知识库**与**数据维度**（必选维度，§7 决策 D5）；文档归属库、库归属组织。
- **文档身份**：`doc_id` 由系统生成（ULID）；**覆盖更新必须显式携带 `doc_id`**（不是按文件名/哈希猜"同一份文档"）；同库同维度下的相同内容默认提示重复、不强制拦截（去重键含库与维度，issue #31 P0-5）。
- 解析：**docling 为主**（进程内 Python 库；docx/pptx/xlsx/HTML 原生解析、结构输出完整）；扫描件走 **MinerU 懒加载**（按需部署 api_server，POC 阶段可不部署）。**M1 验证项**：TXT 的非 UTF-8 编码（GBK 等）识别与转换；`.doc/.xls/.ppt` 老格式明确策略（拒收提示转存新格式，不为此引入 LibreOffice——保零中间件）。
- 切分：结构感知（消费 docling 的标题层级/表格边界/页码）+ 递归 token（256–512）打底；**Excel 单列切分策略**（按 sheet/行块，**每个行块 chunk 重复表头**保留列语义）。
- 嵌入：bge-m3（多语，覆盖中英三态），进程内推理；**模型版本钉死并记录在每个 chunk 上**（embed_model 字段）。
- **摄取阶段拆分（issue #31 P0-4）**：`parse → chunk → index_fts（chunks+FTS 同事务，文档即刻可被 BM25 检索）→ embed（分批）→ index_vec（逐批写向量）→ quality`——各阶段幂等可续；文档状态细分 `searchable_lexical`（词法可搜）与 `searchable_full`（向量就绪）；无向量 chunk 检索时自动只走 BM25 路（RRF 退化为单路）。
- 异步任务化：解析/嵌入/入库不下同步链路；任务表 + worker 子进程（心跳、租约、重试、断点可续——ragflow 样板的最小化）。
- 原始文件与解析产物落本地对象目录（canonical 真相，索引可随时重建）。
- **文档更新与版本化（issue #31 P1-9）**：覆盖更新 → 重摄取 → 新版本 chunk 原子替换；旧版本 chunk 置 **tombstone**（保留可查、标注"已被新版本替代"），agent 历史对话引用的旧 chunk_id 不失效为"不存在"——`fetch` 旧 ID 返回替代提示而非幻觉误判。
- agent 上传的内容标注来源（`source=agent:<id>`）并随检索结果返回来源字段（agent 代传内容可能携带持久化 prompt injection，高敏库可要求人工复核——issue #31 P2）。

### FR-2 检索与重排〔M1〕

- 双路召回：FTS5 BM25（jieba 预分词）+ 向量 kNN（sqlite-vec）；召回窗口给足（参考口径：knn 1024 / rerank 候选 64），召回期不做用户阈值过滤。
- 融合：RRF（k=60，跨实现行业默认）。
- 重排：bge-reranker-v2-m3（进程内，同嵌入的 TEI 升级缝）；分数归一到 [0,1]、**喂 chunk 原文不喂分词文本**。
- 引用溯源：**确定性 chunk_id 优先**（工具输出自带溯源字段：chunk_id、doc_id、标题、页码、片段、分数）——agent 引用不存在的 ID 即幻觉证据。
- 查询变换：LLM 关键词增强（内部网关；对中英混合 query 的漏召回尤其有效）作为首个增强项；多查询扩展按评测数据决定是否加。
- keywords/tags 字段参与 BM25 并配检索加权（ragflow `important_kwd ×5` 模式）。

### FR-3 区分度反馈环〔M1，用户明确要求进 MVP〕

- 入库时检测低区分度 chunk，两路信号、零 LLM 成本：向量拥挤度（新 chunk 与库内近邻的相似度分布）+ 词面通用度（token 平均 IDF）。
- 自动兜底：LLM（内部网关）为低区分度 chunk 自动生成关键词 + 一句定位语（Contextual Retrieval 轻量版）。
- 人工兜底：上传完成页展示**聚合质量报告**（"N 个 chunk 建议补充标注"），点开可补、可忽略——不逐 chunk 打断，不强制。
- 用户标注落 keywords/tags 字段（加权进检索）；表格/目录/条款段天然低区分，提示需容错。
- 前置 schema 动作：keywords/tags 从 M0 起进表结构与 FTS5 索引（后补 = 重建索引）。

### FR-4 维度权限（核心差异化）〔M1 过滤生效，M2 管理面〕

- **模型**：文档级 ACL，维度模型（BI 行级权限 RLS 模式移植到检索层）：
  - 维度定义（dimension，含 `grant_source` 真值源声明）+ 取值枚举（dimension_value，**取值编码用企业主数据码**，如 ISO 国家码/税种码——issue #31 §4.7）元数据化，配置页面 CRUD；
  - 用户授权：用户 × 组织 × 维度 → 取值**集合**（多值）；
  - 文档维度：文档 × 维度 → **取值集合（多值，D19）**，上传时选择——通用政策可同时挂「中国区+海外区」而无需拆分上传；**内容混杂不同维度数据的文档仍须拆分上传（D4）**，多值只用于"内容通用、面向多个维度值开放"的场景。
- **过滤语义（D5+D19 修订）**：文档可见 ⇔ 对**每个「已启用且必选」的维度**，文档取值集合 ∩ 用户授权集合 ≠ ∅（**维度间 AND、维度内 OR**——与用户侧多值授权对称，Glean `allowed_group_intersections` 同构）。编译器只对启用+必选维度生成条件；可选维度不参与过滤（空值即不过滤，不产生"NULL IN 为假"的隐性不可见——issue #31 P1-5）。
- **必选维度（已锁定）**：维度配置为必选时，上传强制选值，不留「未标注」歧义。
- **写权限（issue #31 P1-1，新增）**：上传者可打的维度值**限定在其本人授权集合内**（防越权投放/误标）；超出范围的标注走 org_admin 审批或代标。操作权限矩阵：改文档维度/删除/覆盖上传/重索引 = owner 与 org_admin；维度定义/授权管理 = org_admin；建组织 = 系统管理员。**org_admin 不绕过维度可见性**（管理权与数据可见权分离）；**系统管理员只有管理权没有跨组织数据可见权**（确需查看走临时授权并记审计——issue #31 P1-2）。
- **维度变更是权限事件（issue #31 P1-5）**：新增必选维度须先回填存量文档（默认值或批量指派）再启用，否则全库瞬时不可见；停用维度 = 放宽可见范围，须二次确认 + 影响面预估（将新增多少可见文档、涉及哪些用户）+ 审计。
- **成员关系与授权联动（issue #31 P1-3）**：用户被移出组织时**级联删除**该组织内授权与成员关系（防"移出后重新加入旧权限复活"）；授权行引用 `value_id`（取值改名/删除不悬空；取值只改显示名不改编码）。
- **组织上下文显式传递（issue #31 P1-6）**：REST/MCP 请求**必须显式携带组织**（`X-Org-Id` / 连接配置），缺失即报错——不做"取第一个成员关系"的隐式默认（多组织用户落错组织的风险）；页面可记住上次选择，但 API 层无默认。
- **生效时机（已锁定）**：查询时实时展开用户维度授权为 SQL WHERE（人员调岗即时生效）；文档维度变更 = 更新维度表 + 刷 chunk 冗余过滤字段（便宜的 UPDATE，**不触发重嵌**）。
- **过滤位置红线**：引擎内下推（召回 SQL 内先过滤后取 top-k，向量路为 ACL 过滤后的行集上算距离——issue #31 P0-1），**绝不在应用层 post-trim**；**rerank 前兜底断言**（不该进模型的内容不进模型），返回前再断言一次。
- **agent 代人检索（D8+D18）**：**委托 token（Token Exchange，RFC 8693）**——agent 用用户 token 向 IdP 换取 `aud=knowledge-lattice` 的短期委托 token（`sub`=用户、`act`=agent 标识）；本系统验签后按 `sub` 过滤、`act` 进审计；**禁止 token 原样透传（MCP 规范明令）与请求体携带权限字段**（agent 侧传来的任何权限声明一律忽略——issue #31 P1-7/§5）。静态 token 仅限开发测试。
- **权限真值源模型（D16 深化，issue #31 §4）**：权限拆三件事——**身份**（SSO 透传、验签，不自建账号密码）/ **授权数据**（按维度声明真值源 `grant_source`：与业务系统语义一致的维度【如法人主体、国家】只读同步，一般政策维度本地维护）/ **执行**（永远在本系统引擎内下推）。同步语义：按「用户×组织×维度」幂等全量替换、失败保留旧快照并告警（不清空不放开）；业务口径→维度值走显式映射表；离职调岗经 HR/SSO 事件即时撤销。**永远不做**：查询时实时调业务系统、信任 agent 传来的权限字段。
- owner 兜底：文档 owner 恒可见自己的文档；`acl_entries`（user 级临时共享）表结构保留、初版不启用。
- **权限来源与维护（D16）**：维度授权表由知识库本地维护——管理页单点配置 + CSV/Excel 批量导入导出（初次授权与季度调整的主通道）；登录走企业 SSO，用户档案首次登录自动建档（JIT），管理员不建账号只配授权；与业务系统权限口径的**显式映射**由维护流程承载（导出岗位表→映射转换→导入），不做系统间实时联邦；预留同步适配器（未来权限中心出现时启用，写同一张表）。漂移治理：定期（季度）权限对账 + 查询级审计回放兜底。
- **组织模型（已锁定，D7 再修订）**：多组织 + **用户多组织归属**——用户账号全局唯一，经成员关系（角色 `org_admin`/`member`）属于一个或多个组织；维度定义、知识库、语料池挂组织；**维度授权按「用户 × 组织」作用域独立**（同一用户在 A 组织与 B 组织的角色、授权互不相干，各组织维度体系也不同）。系统管理员跨组织管理（建组织、指定组织管理员）。请求必须携带组织上下文（token 解析用户后按所请求组织校验成员关系），检索/上传/管理均在当前组织内执行。
- **知识库模型（已锁定，D15）**：知识库（dataset）是组织内的业务分组与管理单元（如「VAT 实务库」「费用制度库」），**不承担权限**——权限仍按文档维度 ACL；检索默认跨用户可见范围（组织内），支持按库过滤（MCP `search.datasets` / REST 参数）；对一批文档做独立管理（列表、重索引、删除）以库为单位。

### FR-5 接口面〔M0 MCP，M1 页面〕

- **MCP server**（FastMCP）：四个工具，工具描述按「写给 LLM 看」的纪律撰写（kotaemon DocSearchTool 样板）：
  - `search(query, top_k≤20, datasets?, doc_filter?)`：完整检索配方 + 维度过滤，可限定知识库，返回带溯源字段的命中块；**top_k 服务端硬上限 20**（防一次拖库——issue #31 P1-8）；
  - `fetch(chunk_id, window?)`：按 chunk_id 取上下文窗口（前后 N 个 chunk）——支持 agent「先搜后读」剧本；旧版本 tombstone chunk 返回替代提示（FR-1）；
  - `upload(file_ref, metadata, dataset, dimensions, doc_id?)`：投摄取任务到指定知识库，**file_ref 为文件引用或预签名 URL**（不走 base64），覆盖更新显式带 doc_id；返回 task_id/doc_id；
  - `list_documents(datasets?, status?)`：列出权限内文档（可按库）与处理状态（「先看有什么再搜」剧本）。
  - 工具描述动态注入当前组织的知识库与维度概况，**概况与 `list_documents` 的所有统计（doc_count/chunk_count 等）按调用者权限计算**——不可见文档的存在与数量不得泄露（issue #31 P1-8）；检索参数（权重/阈值类）服务端固定，不对 LLM 暴露噪音旋钮（ragflow 反面教训）。
- **REST**：upload / task status / search / admin（组织、知识库、维度、授权、用户、任务管理）。
- **检索测试页**（薄壳静态页，FastAPI 托管）：输入 query 看命中块与溯源，可按知识库过滤——服务上传者自查，不是聊天产品；UI 永远是薄壳，检索 API 契约先行稳定（quivr 教训）。

### FR-6 治理〔M2〕

- 审计：`audit_events` append-only（**触发器随 M0 schema 一并落地**，不留"上线时再加"），**覆盖查询级**（谁/何时/查了什么/返回哪些来源——quivr 没做的部分补上）；如需防篡改再加**哈希链**（每条含上一条哈希，链头定期锚定外部——issue #31 P1-10）；**审计本身是敏感数据**：定义查询审计的权限（org_admin 本组织 + 系统管理员全局）、保留期与脱敏规则。
- 凭据：模型 key、内部网关凭据走环境变量/secret store，不明文存库（ragflow 反面教材）。
- 出墙：自建零 telemetry，天然干净；依赖清单上线前过一遍出墙体检。

### FR-7 评测〔M1 基线前移，M3 门禁〕

- 分层纪律：检索层（Recall@k / MRR，自算，黄金 chunk 标注的集合运算，秒级零 LLM）与响应层（faithfulness / answer_relevancy，ragas）分开度量。
- **M1 即建小型黄金集**（几十条真实/合成 query + 标注命中 chunk）并跑检索层指标——M1 的检索调参（分词/权重/阈值）必须有度量依据，不能等 M3（issue #31 P2-3）；完整黄金集与响应层指标按 M3 节奏。
- 黄金集：ragas TestsetGenerator 合成候选（双语）→ 人工抽检修正为准；**真实样例语料待用户提供（§9 待决-1）**，到位前以合成集先立基线。
- judge：内部网关 LLM；judge prompt 双语设计，上线前 ~50 条人工双评校准 judge-人一致性（中文场景硬前提）。
- M3：deepeval pytest 断言挂 CI 做变更防护；在线弱信号（引用锚点：引用不存在 ID = 幻觉证据）抽样打标。

## 9. 风险与待决事项

| 区分度检测误报与失真（issue #31 P2 修订） | 相对分位阈值（P25）恒标 ~25%；结果依赖摄取顺序 | 改**绝对阈值 + 分位下限组合**（真实语料校准，bge-m3 相似度分布偏高需重标定）；近邻限定组织内；**定期全量重算**消顺序依赖；新组织冷启动引用全局 IDF；LLM 关键词独立低权重列标来源（llm/user），不与人工关键词混列；口径修正：本机制只补 BM25 关键词，**不等同** Contextual Retrieval 的重嵌入 |
| P95 延迟超标（无 GPU 同步链路：增强+嵌入+rerank） | 检索体验不可用 | NFR-8 全套（rerank 候选 32 / ONNX int8 / 条件触发增强 / 推理进线程池）；M1 实测基线，超标则砍增强、降候选、评估量化 |
| 老格式与编码（.doc/.xls/.ppt、GBK TXT） | 部分语料无法摄取 | M1 定策略：拒收提示转存（不引 LibreOffice 保零中间件）；TXT 编码探测转换进管线 |
| 权限漂移（自建授权表与业务实际脱节，D16） | 调岗后用户仍可见旧维度文档 | 批量导出对账（季度）+ 审计回放兜底；高敏文档从严选维度；grant_sync 适配器留缝；生产前语义匹配维度切只读同步（D16） |
