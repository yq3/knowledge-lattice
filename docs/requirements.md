## 1. 项目定位

**一句话**：私有化部署的企业内部知识库系统（本体）+ RAG 检索能力（能力面），**消费者以 Agent（deepagents）为主、人工检索测试为辅**。

三个定位要点：

1. **本质是知识库，不是 RAG 引擎**。核心资产是文档、权限、维度元数据与摄取管线（canonical 真相）；向量索引只是可重建的投影，检索配方是可替换的能力层。这决定了存储与治理优先于检索花活。
2. **agent 住客户端，知识库做工具服务器**（quivr V2 的反转姿态）：不在本系统内做 agent 循环、聊天界面、workflow 编排；把检索、溯源、鉴权做成值得 agent 信赖的 MCP 工具面。
3. **轻量自建，不做平台**。调研结论：开源五平台（ragflow/dify/anything-llm/quivr/kotaemon）的文档级权限全部缺位、面向人的产品面本需求用不上；自建薄服务可全部覆盖「检索质量 + 治理 + 工具面」三件事。
4. **双层知识供给中的文档知识层（2026-10-16 重定位）**。企业 agent 需要两类知识：**术语理解**（黑话/名词概念/模板名/报表项/表字段映射——结构化条目，精确匹配为主）由姊妹项目 [glossary-agent](../../glossary-agent/) 承担（AC 自动机词典 + 三层渐进披露 + Git YAML/PR 治理）；**文档知识**（政策/操作指南等非结构化内容的语义检索）由本系统承载。两层并行建设、MCP 并挂集成，分工与集成决策见 D17。

性质与投入：lab 仓库 POC 先行，验证后拆仓演进；**全职投入**，MVP 预估 7~8 周（§8）。

## 2. 背景与调研基础

选型判断全部锚定 `research/enterprise-rag/` 调研基线（2026-10 冻结），对本项目影响最大的结论：

| 调研结论 | 对本项目的塑形 |
|---|---|
| 五平台文档级权限全军覆没（dim07）；Google/Azure 托管服务把文档级 ACL 做成原生能力（dim10b） | 维度权限自研，模式照抄托管服务：ACL 随索引摄入 + 查询时引擎内过滤 + 权限增量同步 |
| 检索配方已收敛：双路召回 → RRF(k=60) → cross-encoder 重排（喂原文、分数归一）→ 引用溯源（dim04 + Azure/Anthropic 量化背书） | 检索层不发明轮子，标准配方落地 |
| 解析双服务拓扑：MinerU 管扫描件、docling 管原生文档（dim02） | 本项目扫描件少、Office/TXT 为主 → 简化为 docling 为主、MinerU 懒加载 |
| 中文 BM25 引擎分野 + FTS5 无内置中文分词（dim03） | SQLite FTS5 + jieba 预分词方案，M1 用真实 query 验证中英混排效果 |
| 控制面/数据面分离、摄取任务化、索引可重建是五平台共识（dim01） | 单进程 + worker 子进程 + 任务表的最小实现 |
| OneRAG（126⭐，MIT）评估：形似神不似 | 不采用；借鉴两处——MCP server 模块结构、PDF 解析质量门（mojibake 检测三档处置） |
| **glossary-agent 设计**（lab 仓库，2026-09：Anthropic 16 篇深读 + ChatBI 语义层模式）：术语层方案已完成、POC 未启动；Anthropic Contextual Retrieval 双侧互证（BM25 利短术语 / hybrid+rerank 利文档） | 本系统定位为双层知识供给的**文档层**，与术语层（glossary-agent）并行建设、deepagents 双 MCP 并挂集成（D17）；表名字段名类走术语侧活查询，不进本系统 |

## 3. 用户与场景

| 角色 | 说明 |
|---|---|
| 上传者 | 企业员工，经上传页面（或 agent 代传）投喂文档：先选知识库，再选数据维度，查看处理状态与质量报告 |
| 检索用户（人） | 经检索测试页做简单检索验证（上传后自查），可按知识库过滤；不是聊天问答界面。**同一用户可属多个组织**，在界面上切换组织（左上角），角色与维度授权随组织切换 |
| **Agent（deepagents）** | 企业内部独立部署的 agent 服务（LangChain 系），LLM 走企业内部网关；经 MCP 调用本系统，**代人检索**——请求携带所代表用户的身份 |
| 组织管理员 | 组织内管理知识库、维度定义、用户与维度授权 |
| 系统管理员 | 跨组织：创建组织、指定组织管理员 |

量级：数百用户；语料百万 chunk 以下（超出则走存储升级缝，见 NFR-5）。

核心场景流：

```
人工上传（选知识库 + 选维度）─┐
                    ├─→ 摄取任务队列 → worker：解析→切分→嵌入→入库
agent 经 MCP 上传 ──┘         │（过程中：区分度检测 → LLM 补关键词 → 质量报告提示人工）
                              ▼
人（检索测试页，可按库过滤）─┐   SQLite：元数据 + FTS5 + 向量 + 维度/权限字段
                 ├─→ 检索管线：双路召回 → RRF → rerank → 维度 ACL 过滤（引擎内下推）
agent（MCP，带    │         → 返回带 chunk_id 溯源的结果 + 审计落库
用户 token）─────┘
```

**层级模型（自上而下）**：组织（业务单元，各自一套维度定义与知识库）→ 知识库（业务分组与管理单元，**不承担权限**）→ 文档（权限挂点：维度标签 + owner）→ chunk。

## 4. 语料画像

- **语言三态并存**：纯中文、纯英文、中英混排的文档都有；用户 query 同样三态（含「中文问题带英文术语」的常见形态）。嵌入选型、分词、评测 judge 均按双语设计。
- **格式分布**（按占比从高到低）：纯文本/TXT、Excel、Word、PPT；PDF 少量（原生为主，**扫描件不多**）。
- **来源**：人工上传 + agent 上传；后续可能对接企业系统自动增量同步（演进项，初版不做）。
- **生命周期**：文档会更新——初版只支持人工重新上传覆盖（内容哈希去重、按文档重索引）；删除同理。
- **上传纪律**：一份文件内的数据若分属不同数据维度，**拆成多个文档分别上传**（上传时各自选维度）。不做行级/块级权限（§7 决策 D4）。

## 5. 功能需求

优先级标注：〔M0〕骨架周 /〔M1〕核心能力 /〔M2〕生产化 /〔M3〕质量防线（对应 §8 里程碑）。

### FR-1 文档摄取〔M0 骨架，M2 生产化〕

- 上传接口：REST（人）+ MCP `upload` 工具（agent）；上传时必选**知识库**与**数据维度**（必选维度，§7 决策 D5）；文档归属库、库归属组织。
- 解析：**docling 为主**（进程内 Python 库；docx/pptx/xlsx/HTML 原生解析、结构输出完整）；扫描件走 **MinerU 懒加载**（按需部署 api_server，POC 阶段可不部署）。
- 切分：结构感知（消费 docling 的标题层级/表格边界/页码）+ 递归 token（256–512）打底；**Excel 单列切分策略**（表格型语料按 sheet/行块，区别于文档型）。
- 嵌入：bge-m3（多语，覆盖中英三态），进程内推理（sentence-transformers/FlagEmbedding）；**模型版本钉死并记录在每个 chunk 上**（embed_model 字段）。
- 异步任务化：解析/嵌入/入库不下同步链路；任务表 + worker 子进程（心跳、租约、重试、断点可续——ragflow 样板的最小化）。
- 原始文件与解析产物落本地对象目录（canonical 真相，索引可随时重建）。
- 无 GPU 约束：初始批量嵌入分批跑；摄取期间**检索降级为 BM25 先行**（useful-early 模式，向量索引后台补齐）。
- 文档更新 = 人工重新上传覆盖：content_hash 识别变更 → 重摄取 → 原子替换该文档的 chunk 与索引。

### FR-2 检索与重排〔M1〕

- 双路召回：FTS5 BM25（jieba 预分词）+ 向量 kNN（sqlite-vec）；召回窗口给足（参考口径：knn 1024 / rerank 候选 64），召回期不做用户阈值过滤。
- 融合：RRF（k=60，跨实现行业默认）。
- 重排：bge-reranker-v2-m3（进程内，同嵌入的 TEI 升级缝）；分数归一到 [0,1]、**喂 chunk 原文不喂分词文本**。
- 引用溯源：**确定性 chunk_id 优先**（工具输出自带溯源字段：chunk_id、doc_id、标题、页码、片段、分数）——agent 引用不存在的 ID 即幻觉证据。
- 查询变换：LLM 关键词增强（内部网关；对中英混合 query 的漏召回尤其有效）作为首个增强项；多查询扩展按评测数据决定是否加。
- keywords/tags 字段参与 BM25 并配检索加权（ragflow `important_kwd ×5` 模式）。

### FR-3 区分度反馈环〔M1，用户明确要求进 MVP〕

- 入库时检测低区分度 chunk，两路信号、零 LLM 成本：向量拥挤度（新 chunk 与库内近邻的相似度分布）+ 词面通用度（token 平均 IDF）。
- 自动兜底：LLM（内部网关）为低区分度 chunk 自动生成关键词 + 一句定位语（Contextual Retrieval 轻量版）。
- 人工兜底：上传完成页展示**聚合质量报告**（"N 个 chunk 建议补充标注"），点开可补、可忽略——不逐 chunk 打断，不强制。
- 用户标注落 keywords/tags 字段（加权进检索）；表格/目录/条款段天然低区分，提示需容错。
- 前置 schema 动作：keywords/tags 从 M0 起进表结构与 FTS5 索引（后补 = 重建索引）。

### FR-4 维度权限（核心差异化）〔M1 过滤生效，M2 管理面〕

- **模型**：单库 + 文档级 ACL，维度模型（BI 行级权限 RLS 模式移植到检索层）：
  - 维度定义（dimension）+ 取值枚举（dimension_value）元数据化，配置页面 CRUD；
  - 用户授权：用户 × 维度 → 取值**集合**（多值，如同时有中国区+海外区）；
  - 文档维度：文档 × 维度 → 单值，上传时选择。
- **过滤语义（已锁定）**：文档可见 ⇔ 其**每个**已启用维度的取值都在该用户的授权集合内（**AND**）。
- **必选维度（已锁定）**：维度配置为必选时，上传强制选值，不留「未标注」歧义；可选维度不参与过滤。
- **生效时机（已锁定）**：查询时实时展开用户维度授权为 SQL WHERE（人员调岗即时生效）；文档维度变更 = 更新维度表 + 刷 chunk 冗余过滤字段（便宜的 UPDATE，**不触发重嵌**）。
- **过滤位置红线**：引擎内下推（召回 SQL/向量过滤条件内），**绝不在应用层 post-trim**；rerank 前二次校验兜底（进 prompt 的每个 chunk 必过 ACL）。
- **agent 代人检索**：agent 请求透传用户 token → 验签 → 解析用户 → 展开维度 → 过滤（token 形态与 agent 服务约定，M2 前敲定，见 §9）。
- owner 兜底：文档 owner 恒可见自己的文档；`acl_entries`（user 级临时共享）表结构保留、初版不启用。
- **权限来源与维护（D16）**：维度授权表由知识库本地维护——管理页单点配置 + CSV/Excel 批量导入导出（初次授权与季度调整的主通道）；登录走企业 SSO，用户档案首次登录自动建档（JIT），管理员不建账号只配授权；与业务系统权限口径的**显式映射**由维护流程承载（导出岗位表→映射转换→导入），不做系统间实时联邦；预留同步适配器（未来权限中心出现时启用，写同一张表）。漂移治理：定期（季度）权限对账 + 查询级审计回放兜底。
- **组织模型（已锁定，D7 再修订）**：多组织 + **用户多组织归属**——用户账号全局唯一，经成员关系（角色 `org_admin`/`member`）属于一个或多个组织；维度定义、知识库、语料池挂组织；**维度授权按「用户 × 组织」作用域独立**（同一用户在 A 组织与 B 组织的角色、授权互不相干，各组织维度体系也不同）。系统管理员跨组织管理（建组织、指定组织管理员）。请求必须携带组织上下文（token 解析用户后按所请求组织校验成员关系），检索/上传/管理均在当前组织内执行。
- **知识库模型（已锁定，D15）**：知识库（dataset）是组织内的业务分组与管理单元（如「VAT 实务库」「费用制度库」），**不承担权限**——权限仍按文档维度 ACL；检索默认跨用户可见范围（组织内），支持按库过滤（MCP `search.datasets` / REST 参数）；对一批文档做独立管理（列表、重索引、删除）以库为单位。

### FR-5 接口面〔M0 MCP，M1 页面〕

- **MCP server**（FastMCP）：三个工具，工具描述按「写给 LLM 看」的纪律撰写（kotaemon DocSearchTool 样板）：
  - `search(query, top_k, datasets?, doc_filter?)`：完整检索配方 + 维度过滤，可限定知识库，返回带溯源字段的命中块；
  - `upload(file, metadata, dataset, dimensions)`：投摄取任务到指定知识库，返回 task_id/doc_id（ragflow MCP 没有上传工具，这是面向 agent 的差异点）；
  - `list_documents(datasets?, status?)`：列出权限内文档（可按库）与处理状态（「先看有什么再搜」剧本）。
  - 工具描述动态注入当前组织的知识库与维度概况；检索参数（权重/阈值类）服务端固定，不对 LLM 暴露噪音旋钮（ragflow 反面教训）。
- **REST**：upload / task status / search / admin（组织、知识库、维度、授权、用户、任务管理）。
- **检索测试页**（薄壳静态页，FastAPI 托管）：输入 query 看命中块与溯源，可按知识库过滤——服务上传者自查，不是聊天产品；UI 永远是薄壳，检索 API 契约先行稳定（quivr 教训）。

### FR-6 治理〔M2〕

- 审计：`audit_events` append-only（触发器防篡改，quivr 模式），**覆盖查询级**（谁/何时/查了什么/返回哪些来源——quivr 没做的部分补上）。
- 凭据：模型 key、内部网关凭据走环境变量/secret store，不明文存库（ragflow 反面教材）。
- 出墙：自建零 telemetry，天然干净；依赖清单上线前过一遍出墙体检。

### FR-7 评测〔M1 基线，M3 门禁〕

- 分层纪律：检索层（Recall@k / MRR，自算，黄金 chunk 标注的集合运算，秒级零 LLM）与响应层（faithfulness / answer_relevancy，ragas）分开度量。
- 黄金集：ragas TestsetGenerator 合成候选（双语）→ 人工抽检修正为准；**真实样例语料待用户提供（§9 待决-1）**，到位前以合成集先立基线。
- judge：内部网关 LLM；judge prompt 双语设计，上线前 ~50 条人工双评校准 judge-人一致性（中文场景硬前提）。
- M3：deepeval pytest 断言挂 CI 做变更防护；在线弱信号（引用锚点：引用不存在 ID = 幻觉证据）抽样打标。

## 6. 非功能需求

| # | 需求 | 口径 |
|---|---|---|
| NFR-1 | 部署形态 | 企业内网 Linux 服务器，**无 GPU**；**零中间件**：目标形态 = 1 个 FastAPI 进程 + 1 个 worker 子进程 + 1 个 SQLite 文件，无任何外部常驻服务（TEI/MinerU 容器是升级路径不是依赖） |
| NFR-2 | 容量 | 百万 chunk 以下、数百用户；sqlite-vec 为暴力扫描（无 ANN），十万级向量以上需实测边界，超限走存储升级缝 |
| NFR-3 | 嵌入吞吐 | 无 GPU 下初始批量建索引以天计的量级风险：摄取必须分批 + useful-early 降级（BM25 先可搜） |
| NFR-4 | 可二改性 | 代码量控制在团队能读完、能改的程度；存储访问收敛在 repository 接口后（hybrid_search / insert / delete_by_doc） |
| NFR-5 | 演进缝（配置级/接口级切换，不改核心） | 存储 → pgvector / milvus 2.5+（jieba BM25 + 库内融合）；嵌入与重排 → TEI 容器；解析 → MinerU 档位/VLM；企业系统增量同步；SSO/IdP 对接（含组织/成员关系从 IdP/HR 同步）；user 级临时共享 |
| NFR-6 | 安全 | 权限过滤引擎内下推红线（§FR-4）；凭据治理（§FR-6）；上传校验（类型/大小）；预留输入侧防护（prompt injection 为已知缺口，MVP 标注不实现） |
| NFR-7 | License | bge 系 Apache-2.0 相对安全；docling 系模型权重 license **未核实**（IBM 系有 CC-BY-NC 历史先例）——POC 内用可接受，商用前逐卡上 HF 核实（调研最大遗留风险） |

## 7. 已锁定的决策记录

| # | 决策点 | 结论 | 依据 |
|---|---|---|---|
| D1 | 技术栈 | Python（FastAPI） | Agent 时代生态主流；开源 RAG 产品同栈，参考件丰富 |
| D2 | 部署 | lab POC 先行；Linux 无 GPU；零中间件 | 用户环境约束；SQLite 一把梭方案 A 命中该约束 |
| D3 | 权限粒度 | 权限不按知识库切分（库级权限是维度过滤的特例，见 D15），采用文档级维度 ACL；**不做 chunk 级**（跨 chunk 上下文泄漏、重切分漂移、不可运营） | Google/Azure 托管模式 + 调研 dim07/10b；业界无 chunk 级先例 |
| D4 | 混维度文档 | 拆成多文档分别上传，上传时选维度 | 权限边界与内容自然边界重合纪律；消灭行级权限问题 |
| D5 | 维度组合语义 | AND（每个维度命中才可见）；必选维度上传强制选值 | 严格默认防泄露；缺一个维度即泄露 |
| D6 | 权限生效时机 | 查询时实时展开（用户侧即时）；文档侧变更刷冗余字段不重嵌 | ACL 冗余进索引 + 增量同步（托管服务模式） |
| D7 | 组织模型 | **多组织 + 用户多组织归属**（再修订 2026-10-16）：组织=业务单元/工作区，语料池、知识库与维度定义挂组织；用户账号全局唯一、可属多个组织（成员角色 `org_admin`/`member` 按组织独立）；**维度授权作用域 = 用户 × 组织**——同一用户在不同组织的角色与数据权限互不相干；系统管理员跨组织；切换组织后整个权限上下文随之切换 | 用户确认：一人在多个组织/业务单元有不同角色与数据维度权限，且各组织维度体系不同 |
| D15 | 知识库模型 | 多知识库：dataset 挂组织、文档挂库；库是业务分组与管理单元，**不承担权限**（权限仍按文档维度）；检索支持按库过滤 | 用户确认需要多知识库；库级权限是维度过滤特例，权限职责归维度模型避免双重体系 |
| D16 | 权限来源 | **知识库自建维度授权表**：登录走企业 SSO（用户档案首登 JIT 落库，不建独立账号密码），授权（用户×组织→维度值）由管理页 + 批量导入维护；**业务系统角色不搬入**（操作权限≠数据可见性，如需引入须经显式映射）；预留同步适配器作为演进缝 | 用户确认；调研开源五家全部自建；文档以人工上传为主、无现成 ACL 可同步；数百用户规模下维护成本可控 |
| D17 | 双层知识供给架构（2026-10-16） | agent 知识分两层：**术语层归 glossary-agent**（Git YAML+PR 治理、AC 自动机精确匹配、三层渐进披露），**文档层归本系统**（混合检索+维度 ACL）；表名字段名类（真值在源系统、高频变、量大）走术语侧 MCP 活查询数据字典、**不静态导入**任一侧；集成 = deepagents 并挂两个 MCP server（演进缝：本系统加载术语运行时投影统一暴露，Git 真值源不动）；L0 常驻核心术语表由术语库构建期导出进 agent system prompt | 用户确认两类需求并存（黑话词典 + 政策文档）；两轮调研互证（Anthropic Contextual Retrieval：BM25 利短术语、hybrid+rerank 利文档）；不合并系统以保 glossary 的 Git 治理闭环 |
| D8 | agent 身份 | 代人检索（透传用户 token），非服务账号 | 用户角色与数据维度权限随人走 |
| D9 | 维度元数据 | 配置页面 CRUD（维度/取值可自定义），通用化 | 不同业务单元维度定义不同 |
| D10 | 区分度反馈环 | **进 MVP**（检测 + LLM 兜底 + 聚合人工提示） | 用户明确要求；ragflow 加权字段 / Contextual Retrieval 同构背书 |
| D11 | 解析拓扑 | docling 为主（进程内），MinerU 懒加载 | 语料以 Office/TXT 为主、扫描件少；docling 格式面正好覆盖 |
| D12 | 嵌入 | bge-m3 多语，进程内推理，钉版本 | 中英三态；无 GPU 约束；quivr 钉版本先例 |
| D13 | 项目名 | knowledge-lattice | GitHub 精确零同名 + PyPI 空；晶格隐喻贴合「知识库本体」定性 |
| D14 | OneRAG | 不采用，列为参考实现（MCP 模块结构 + PDF 质量门两处借鉴） | 形似神不似：缺维度 ACL/中文/结构化解析，路线相反（广度适配 vs 单栈深度） |

## 8. 里程碑与验收口径（全职，预估 7~8 周）

| 里程碑 | 内容 | 验收口径 |
|---|---|---|
| **M0**（第 1 周） | 骨架端到端：上传（选库+维度）→ docling 解析 → 结构感知切分 → 进程内嵌入 → SQLite 入库 → 单路向量检索 → MCP `search` 接通 → 检索测试页。**schema 一次性落全**：组织、知识库、维度表、ACL 字段、keywords/tags、embed_model、任务表、审计表 | deepagents 经 MCP 完成一次带 chunk_id 溯源的检索问答；测试页能人工验证召回 |
| **M1**（第 2~3 周） | 完整检索配方（jieba FTS5 + 双路 + RRF + rerank + 关键词增强 + 按库过滤）；**维度 ACL 过滤生效**（上传选维度、查询按用户维度过滤）；**区分度反馈环**（检测 + LLM 补关键词 + 质量报告页）；真实文档批量上线 | 权限越权用例全绿（无权用户在检索结果、MCP 返回、引用三个面都拿不到受控内容）；**20~50 条真实中英 query 的 BM25/混合检索人工标注验证**（jieba 中英混排效果实证）；区分度检测误报率可接受（人工抽查） |
| **M2**（第 4~6 周） | 异步任务系统完整化（心跳/租约/重试/断点续跑）；**管理面：组织管理（系统管理员）、知识库管理、维度配置、用户授权（含批量导入导出）、任务管理**；**SSO 对接（协议待确认，token 验签 + JIT 建档；静态 token 降为开发/测试与 agent 场景）**；agent 代人身份透传（MCP 鉴权与 token 约定落地）；审计落库；文档更新覆盖重索引；分批摄取 + useful-early 降级 | 任务断点可续（杀 worker 不丢任务）；审计可回放一次完整检索；文档更新后新旧 chunk 原子替换；无权 token 在 MCP 面被正确过滤；**跨组织隔离用例全绿**（A 组织用户/agent 检索不到 B 组织任何内容）；SSO 登录→建档→授权→检索全链路通；批量导入 500 行授权正确生效 |
| **M3**（第 7~8 周） | 评测体系：黄金集（合成 + 人工修正）基线；检索层 Recall@k/MRR + 响应层 faithfulness；judge 双语校准（~50 条人工双评）；deepeval 门禁进 CI；在线引用锚点抽样 | 门禁能卡住一次人为注入的检索层回归；judge-人一致性达标（一致率/κ 过阈值）；黄金集覆盖中英三态 query |

> M1 的「真实文档批量上线」依赖待决-1（真实样例语料）；未到位时以合成/公开样例先行，验收口径中依赖真实数据的部分顺延。
>
> **路线注记（2026-10-16，D17）**：本系统与 glossary-agent（术语层，其 POC 约 1~2 周）**两线并行**——术语层链路短可先行探路；本 M0~M3 按上文节奏照常推进，互不阻塞。

## 9. 风险与待决事项

**待决（需要输入）：**

1. **真实样例语料与业务问题**（用户提供）：解析抽检（50~100 份含代表性格式）与黄金集的原料；未到位前 M1/M3 相关验收顺延。
2. **企业 SSO 协议与 token 属性**（D16/登录链路前置）：OIDC / CAS / 自研？token 里除 userId 外还带什么（部门/组织/显示名）？决定 M2 的验签与 JIT 建档字段映射。
3. **agent 身份 token 形态**：agent 服务透传的用户身份是什么（JWT / 内部网关 header / 自定义 token），M2 前与 agent 服务约定；用户档案来源已定（SSO + JIT，D16），此项只剩 token 传递形态。
4. Python 包名（`knowledge_lattice` / `klattice`）与代码内简称——方案设计时定。

**风险登记：**

| 风险 | 影响 | 缓解 |
|---|---|---|
| 无 GPU 嵌入吞吐（百万 chunk 以天计） | 初始建索引周期长 | 分批摄取 + useful-early（BM25 先可搜）；评估轻量嵌入模型（如 multilingual-e5-small）作权衡项 |
